Notes · AI governance

Before an AI agent touches claims data

The question a board asks about AI is rarely "does it work". It is "what is it touching, who can stop it, and can we prove what it did". Those are governance questions, and the good news is that they have concrete answers that fit on one page.

The two failure modes

The first is sprawl. Agents are cheap to build, so within months there are a dozen, each reading data nobody catalogued, sending outputs nobody reviewed, owned by whoever built it. The second is the reaction to the first: a blanket ban, which loses the value and does not stop the sprawl, because the agents move to personal accounts. The middle path is a small standard, enforced in the system rather than described in a policy, with an executive who owns it.

Seven controls

  1. A named owner. A person, not a team, who can be paged when the agent fails and who resets the switch when it is fixed.
  2. Data access scoped and enforced at run time. The agent may read the data classes on its list and no others. Not a paragraph in a policy: a check that runs before every read and refuses what is not on the list.
  3. A kill switch with a price tag. Anyone can turn a thing off. The control is knowing, before it is needed, what stops working downstream and how many people-hours a day the manual fallbacks cost. Without the price tag, the switch will not be thrown when it should be.
  4. A per-run log. Who, what, on which data, to which destination, and what the rules decided. This is the artefact an examiner asks for, and the one that proves the second control is real.
  5. A person signs before anything leaves the company. Internal reports can refresh automatically. An export to the actuary, a certificate to a counterparty, an invoice query to counsel: these wait for a signature.
  6. Tests that must pass before a switch is reset. An agent that failed is not returned to service because someone thinks it is fixed.
  7. A documented manual fallback. With an owner and an hours estimate, so the third control has a number in it.

What "enforced" means

Most AI governance fails at the gap between the document and the system. The policy says the agent may not send claimant names outside the company; nothing in the system stops it. Enforced means the rule is code that runs on every action, and a refused action is a logged event that pages the owner. The difference is the difference between a control and a hope.

The operating model around the controls

A proposal on one page: what the agent does, what it reads, where its output goes, who owns it, what the fallback is. A classification by data sensitivity and by whether any output leaves the company, which decides the controls required without a debate each time. A standing committee, with the chief risk officer and the general counsel on it, that decides scope and records the decision as the agent's enforced authorisation. A pilot with every gate on. Production only when every control passes. A quarterly review, with a failed control sending the agent back to pilot.

What an examiner asks to see

The list of agents and their owners. The data authorisation matrix, approved and dated. The log for a day they choose. Evidence that a refused action was refused. The fallback for the one that matters most. A company that can produce those in an afternoon has a programme; a company that cannot has a collection of scripts.

The Agent Control Plane runs a synthetic fleet of ten agents under exactly these controls: throw a switch, inject a fault, and read the log.

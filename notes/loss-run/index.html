Notes · Claims data

The loss run cannot be trusted as delivered

Every number a captive reports, reserves, or prices a renewal from starts with one spreadsheet: the administrator's loss run. It is the raw material for the actuary, the finance team and the board. And it is never clean.

What arrives

A few thousand rows, one per claim. Dates in whichever format the adjuster's screen used that day. Amounts as text, some with dollar signs, some in parentheses for negatives, some with a stray space. The same operating company spelled three ways. Status written as "Open", "OPEN", "O" and "Open " with a trailing space. A handful of claims that appear twice, with the older copy carrying stale numbers. A claim with no number at all. A paid amount that is negative because a recovery was posted as a payment. A total-incurred column that does not equal paid plus reserve, because it was computed on a different day.

None of this is malice or incompetence. It is what a file looks like when it has been touched by many hands over many years, and exported from a system that was never designed to feed yours.

What happens when nobody checks

Someone opens it, fixes what they notice, pastes it into a workbook, and emails the totals. Two things follow. The first is that the errors nobody noticed become the company's numbers. A duplicate row overstates incurred; a negative payment understates it; a row with a blank claim number silently vanishes from every report that keys on claim number. The board sees a figure that is wrong by an amount nobody can name.

The second is worse: the process depends on the person. When they are away, the file is not processed, or it is processed by someone who does not know which columns lie. The actuary receives a different cut from the one the board saw. Within a year there are three versions of the truth and a standing argument about which one is right.

What a fit-to-use file looks like

Every date in one format. Every amount a number. Every label from a fixed list. Every operating company resolved to a code. One row per claim, with a stated rule for which copy wins when there are two. Incurred recomputed, always, as paid plus reserve, and the administrator's own incurred column used only to detect disagreement. Personal data recognised and kept out of every export that leaves the company.

And, separately, a list of what was wrong. Not a count: a list, by row and by rule, with what was done about each. That list goes back to the administrator the same morning. Over months the file gets better, because for the first time someone is telling them what is wrong with it.

Why the fix is a gate, not a person

The instinct is to hire someone careful. The better answer is a pipeline that standardises the file the same way every day, validates it against rules that grew out of the defects actually seen, and refuses to release when something blocking is found. A blank claim number, a negative payment, a claim reported before its loss date: these quarantine the row and hold the whole release until a named person clears them. Everything else is corrected and listed.

The person is still there. They are just doing the part only a person can do: deciding what to do with the twelve rows that could not be loaded, rather than retyping two thousand that could.

What it changes for the decision

The board reads the same export the actuary reads. The renewal is negotiated from internal numbers that reconcile to the ledger, rather than from the carrier's. And when the numbers move, the activity brief says why: which claims were reported, which closed, which reserve moved by more than the threshold. That is a different conversation from "the total went up".

The Loss-Run Pipeline does all of this on a synthetic file with the defects above deliberately injected, and accepts a file of your own.
